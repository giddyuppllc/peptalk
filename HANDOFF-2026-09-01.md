### Versioning — check this before building

`eas.json` sets `appVersionSource: remote`, so **EAS owns buildNumber and
versionCode** and their absence from app.json is correct. The 26 Aug builds went
out as **1.10.0** while app.json said 1.9.9 — that is where the "phantom 1.10.0"
came from. app.json is now **1.10.1**. Run `eas build:version:get` and make sure
what EAS will stamp is what you intend before you build.

## 5. What was fixed this session

**Money and entitlements**
- **A store-distributable build was giving Pro away.** `EXPO_PUBLIC_ENV !==
  'production'` granted Pro to every signed-in user, and eas.json's `preview`
  profile pairs that env with `distribution: "store"`. Now pinned to `__DEV__`.
  Web was never affected; **Android was**.
- The grant was WRITTEN to persisted state with `expiresAt: null` — never
  expires — so anyone who ran a preview build once kept free Pro forever after
  updating. Now purged on load by product id.
- `square.ts` defaulted the Square **location** to the sandbox one while
  production is different. A build setting env + app id but missing the location
  var would tokenize cards against the wrong location, silently. Guarded.

**The 2.1(a) login bug, most likely root cause found**
- `signInWithPassword` had **no timeout**, and supabase-js sets none. On a
  half-connected network it neither resolves nor rejects: the user taps Log In
  and *nothing happens*. That is, word for word, "redirected back to the login
  page after logging in". Bounded at 20s.
- Same class found in 25 `functions.invoke` sites (fixed once at the client) and
  17 raw `fetch` calls (fixed per site). None had a timeout.
- Session persistence verified on an ERASED device across 4 cold starts, both
  platforms.

**Database**
- Migration ledger repaired — `supabase db push` is safe again.
- Checking objects before repairing found `20260804000010_community_owner_update_guard`
  had **never been applied**: without it, any user could self-approve their own
  pending-image post via raw PostgREST, defeating the AI moderation Apple
  requires. Applied and verified by running the attack in a rolled-back
  transaction.
- 5 edge functions were live with **no source anywhere**. Recovered from their
  deployed bundles into `supabase/functions/_recovered/` (transpiled, outside
  the deploy path on purpose).

**Everything else**: HealthKit false "access revoked", Android strings on iOS
surfaces, IAP retry + already-owned, the PT navigation sheet, CSP, raw error
text shown to users at 17 sites, notification permission being requested before
the user had done anything, two require cycles through the auth store, and PWA
auto-update.

## 7. The thing worth internalising

Six separate cases this session of a check reporting success or failure for work
it did not do:

1. `login.yaml`'s `visible: "Sign In"` never matched, so it SKIPPED the entire
   login and passed on any device holding a session — a release-blocker test
   that never tested the thing it blocks on.
2. `verify-edge-functions`' remote half never ran — it parsed the CLI payload
   wrongly, threw, and reported "skipped — no token". The five orphaned
   functions it was written to catch went unreported for months.
3. A scanner I wrote could pass having read zero files.
4. My first invoke-timeout patch mutated a throwaway object, and the test
   asserted the source *contained* the patch rather than that it worked.
5. RN's LogBox — a native overlay that swallows touches — made a working app
   look like a hard product bug for hours.
6. A percentage-coordinate tap made working AI generation look broken.

And three production artifacts that correspond to no source anyone has: the
phantom 1.10.0 binary, the five edge functions, and the previously-live PWA
(stamped `5a993f4a`, a commit in no branch).

When a suite is green, ask what it actually executed.

## 9. The repo had drifted from production — mostly fixed, five files need you

`npm run check:drift` (new) reads the original source back out of each deployed
Supabase function and compares it to this repo. Every other check here compares
the repo against itself; this is the only one that asks whether the repo still
matches what is running.

**It found 934 lines of production code that did not exist in this repository**,
plus five functions with no source here at all. A routine
`supabase functions deploy` of any of them would have silently reverted
production.

### Fixed — 52 of 60 functions now match production exactly

- **49 functions** were missing the Sentry error-reporting wiring. Two lines
  each, deployed across the estate and never committed, and `_shared/sentry.ts`
  did not exist here at all. **That is very likely why backend failures have been
  hard to see.** Applied from the deployed source verbatim, and only where every
  added line was provably that wiring.
- **`validate-purchase` (+346)** and **`apple-notifications` (+26)** were strict
  supersets — every repo line verified to survive before replacing.
- **`square-webhook`** looked like a two-way change but was not; nothing was lost.
- **Five orphaned functions recovered in full** — `aimee-usage`,
  `credit-autorefill`, `credit-autorefill-settings`, `reconcile-purchases`,
  `send-welcome-email` — plus three shared modules (`credits.ts`, `email.ts`,
  `sentry.ts`) that were missing outright. These are ORIGINAL source, not
  reconstructions: Supabase's bundles embed source maps, and the method was
  validated byte-identical against a control file. They sit in
  `supabase/functions/_recovered/`, outside the deploy path, for you to promote.

### Not fixed — five files, and this needs judgement, not effort

```
aimee-chat-stream/_cost.ts   145 → 321
aimee-chat-stream/index.ts   738 → 848
square-subscribe/index.ts    160 → 252
square-checkout/index.ts     101 → 132
_shared/credits.ts           128 → 137
```

Both sides have lines the other lacks, so neither can be taken wholesale.
**Production is NOT uniformly newer** — `_shared/credits.ts` carries a decision
dated 2026-08-26 ("ONE PACK, $4.99 — Edward's call") that production does not
have, meaning the deployed copy is the older one there.

`docs/DRIFT-REVIEW.md` shows, per file, only the repo-only lines — the ones at
risk — and each deployed copy is saved beside its function as `*.deployed.ts`.
Three of the five are payment paths.

### The cause, which is the part worth fixing

Code reached production without being committed, repeatedly, from a working copy
on someone's machine. The same fingerprint is on every artifact that carries a
build stamp: the previously live PWA was stamped `5a993f4a`, a commit in no
branch of this repo.

`check:drift` measures the gap. It cannot prevent it. **Until publishing happens
only from committed code — CI, or a deploy that refuses a dirty tree — this
rebuilds itself.** That is the one decision here with a lasting effect.
